# Technical debt register

Items here are **not** security controls and are **not** Phase 1 gate blockers unless stated. Each has an owner decision point so it does not become permanent by default.

## TD-001 — WSL2 networking on the development workstation is extremely slow
* **Observed:** network requests from inside WSL2 (Ubuntu) take roughly 30–50 s each (package index/downloads are impractical). Observed during Phase 1 on this Windows 11 machine; the cause has **not** been diagnosed.
* **Impact:** PostgreSQL 16 lives in WSL2 (installed earlier); installing anything else inside WSL (extra PostgreSQL extensions, PgBouncer, Redis, a container engine) is impractical. This is why the pooler test (B-03), the Redis-down throttling test (B-04) and the container build (B-07) could not run locally.
* **Current workaround (accepted by the project owner for now):** Python runs natively on Windows via `uv` (tool downloads work on Windows) and connects to the WSL PostgreSQL through localhost forwarding.
* **Fragility of the workaround:** forwarding to WSL only works **while a WSL session is open**; a long-running `wsl … sleep` session must be kept alive, and it expires. The WSL VM may also stop when idle. A cluster created for rehearsals lives in `/tmp` inside WSL and disappears on shutdown. Documented in `OPERATIONS_NOTES.md`.
* **Why it is not a Phase 1 blocker:** the PostgreSQL-dependent security tests (RLS, roles, triggers, audit) run against a real PostgreSQL 16.15 with the real least-privilege roles and pass; CI is intended to run them again on a clean runner (P2-1).
* **Things to try when someone has time (none attempted yet — these are hypotheses, not findings):** WSL mirrored networking mode (`networkingMode=mirrored` in `.wslconfig`), DNS tunneling / `generateResolvConf` and resolver settings, MTU mismatch with VPN software, IPv6 vs IPv4 preference, antivirus/firewall interaction with the WSL virtual adapter, `wsl --update`, and as a fallback a native Windows PostgreSQL 16 or Docker Desktop with the WSL2 backend.
* **Exit criterion:** a command such as `apt-get update` completes in seconds from inside WSL, or the project adopts a different local database setup that does not depend on WSL networking; then update `OPERATIONS_NOTES.md` and close this item.
* **Parity risk to remember:** developing against a different PostgreSQL build than production is a risk in itself; the production database version/hosting is open item O-4.

## TD-002 — `makemigrations --check` in CI emits a RuntimeWarning
* The step runs before the throw-away test database exists, so Django warns that it cannot check migration consistency for the `owner` connection. The command still exits 0 and detects model/migration drift. Cosmetic; fix by ordering the step after database creation or by using `--skip-checks` semantics if it becomes noisy.

## TD-003 — Generated documents are regenerated by scripts but several narrative documents are hand-written
* `PHASE1_SECURITY_GATE.md`, `OPEN_ITEMS.md`, `OPERATIONS_NOTES.md` and the plans are hand-maintained and can drift from the generated reports. Mitigation today: the gate document cites generated artefacts for every number. Consider generating the gate's evidence table from `gate_summary.json` and the three record checkers.

## TD-004 — Pending-spec bodies are unexecuted
* The statements in `tests/test_pending_controls.py` after each `require_*` call have never run against an implementation. When a feature is built they need a first real run and likely small corrections (fixture names, response shapes). This is expected and is why the specs are reported as XFAIL, not as coverage.

## TD-002 — Dev-only components that stand in for production services (not gate blockers; production start-up refuses all of them)
Local key provider, file signer, rewritable export directory, local evidence store, EICAR scanner, log-only alerts, locmem e-mail. Each is tied to an open item (O-4, O-7, O-11) and a control gap in `control_map.yaml`; none may be described as a production control.
